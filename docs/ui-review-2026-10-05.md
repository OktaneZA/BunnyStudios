# Storybook review — 5 October 2026

Scope: continued review of the Storybook on commit `a08df61`, using the saved
screenshots in `screenshots/ui-review-2026-10-05/` and current source. This continuation
did not operate the live application, spend money, or change story content. Findings
below distinguish visible problems from source-level risks. The Storybook rebuild
requirements supersede the older Create/Put it together layout requirements.

## Findings

### P2 — Light-theme links still have low contrast

`styles.css:35` keeps `--accent: #b5a0ff` in the white theme, and `.link-button`
at line 961 uses that colour for text. This is approximately 2.23:1 against white.
The saved light screenshots show faint **Who's in it** and **Add a page here** links.
Use a darker light-theme text token, keeping the current accent for filled buttons
where dark text is used. Check all link-button instances in the cover and sheets.

Evidence: [light editor](screenshots/ui-review-2026-10-05/03-edit-light-1024.png)
and [768px editor](screenshots/ui-review-2026-10-05/09-edit-768.png).

### P2 — Cover autosave can overwrite a newer local draft

`StoryCover.tsx` sends `saveWords()` directly on each title/summary blur, with no
serialization or request ordering. Every returned project is passed to `onProject`;
the effect watching `project.title` and `project.logline` then resets both local fields.
For example, blur a changed title, then start writing the summary before that request
returns: its response contains the previous summary and resets the in-progress text.
Overlapping blur requests can also send the same stale field values in both patches.
This is a source-level finding; a delayed-network browser reproduction remains to be run.

Serialize cover saves and retain edits made after a request starts. Only synchronize
server values into fields with no newer local changes. Failed cover writes should
retain recoverable drafts, as scene autosave already does.

### P2 — The make action is below the editor at 768px

In the saved 768px editor, scene name, action, details and length consume the screen;
**Make your clip** begins near the bottom and its button extends below the viewport.
The 1024px image shows the better arrangement: the action and make panel side by side.
This is a tablet usability concern, rather than evidence that the explicit 1024×768
SB-12 requirement fails. Consider a compact priced action near the writing fields
when the layout stacks. Keep any blocking explanation adjacent to it.

Evidence: [768px](screenshots/ui-review-2026-10-05/09-edit-768.png),
[1024px](screenshots/ui-review-2026-10-05/02-edit-1024.png).

### P3 — The active page loses its accessible heading reference

`StoryPage.tsx` always sets `aria-labelledby="page-title-{scene.id}"`, but renders
that target only in the folded summary. When selected, the page renders its children
instead; `SceneComposer.tsx` uses a different heading id, `composer-{scene.id}`.
Point the selected article at that heading or render a persistent page heading.
This is confirmed by the render branches; a screen-reader session was not run.

## What to preserve

The 1024px editor places writing and generation together. The cover folds away,
selected media has explicit Video/Picture state language, and page movement has
visible buttons. These address several problems in the previous interface.

## Next verification

Prioritize cover draft preservation, then light-theme contrast. Reproduce cover
saves with delayed responses, check keyboard names when pages expand, and check
the stacked editor on a physical tablet. Saved screenshots alone do not establish
touch usability, generation completion, download behaviour or playback continuity.
